# Ревью проекта и план доработки

**Проект:** «Прототип ИИ-системы диагностики ошибок конфигурации на основе индуктивного логического программирования (Prolog)»
**Что проверялось:** техническое задание из `Техническое_задание_Prolog_ILP_диагностика.docx` и реализация в папке `prolog-ilp-diagnostics`.
**Дата ревью:** 10.11.2026.

---

## 1. Короткий вывод

Проект **существенно сильнее, чем следует из его собственного README**. Это не макет и не набор кнопок: сквозной сценарий «демо-набор → обучение в SWI-Prolog → правила → диагностика нового проекта → сравнение с Decision Tree → экспорт» действительно работает. На реальном SWI-Prolog 10.0.2 проходят 23 теста `plunit` и 46 тестов `pytest`, а полный сценарий интерфейса (загрузка 500 проектов, обучение, диагностика), проверенный через `streamlit.testing`, завершается без исключений и находит ожидаемые правила.

По функциональным требованиям ТЗ закрыто практически всё: FR-01–FR-24 закрыты по существу (два пункта — с замечаниями), AC-01–AC-12 выполнены, включая главное требование — **правила не написаны заранее, а выводятся Prolog-движком из E+/E− и фоновых знаний**. Сильные стороны — канонизация изоморфных тел, отсечение по монотонности покрытия, честная обработка ошибок запуска Prolog, JSON-протокол через временные файлы и независимая проверка метрик в тестах.

Главные проблемы лежат не в алгоритме, а в **артефактах поставки, отдельных семантических деталях и глубине эксперимента**:

1. README описывает проект как «не проверенный на настоящем SWI-Prolog / Streamlit», хотя сейчас всё проверяется и работает. Для принимающей стороны это выглядит как незакрытый риск, хотя риск уже снят.
2. `examples/` сгенерированы вспомогательным интерпретатором на Linux (`environment.swi-prolog = "… (mini-interpreter stand-in)"`), а не реальным SWI-Prolog. Для поставки на Windows это нужно перегенерировать.
3. Демонстрационный сценарий в README расходится с формой диагностики: форма по умолчанию содержит `API_TOKEN` одновременно в «требуемых» и «отсутствующих», поэтому показывает **две** ошибки, а README обещает только `missing_dependency`.
4. В интерфейсе не реализован третий статус из п. 7.2 ТЗ — «недостаточно данных»: при неизвестных полях показывается «не обнаружен обученными правилами» плюс предупреждение.
5. Экспорт модели односторонний: модель нельзя загрузить обратно и применить к новым проектам.
6. Демо-набор всегда даёт правила длины 2 и идеальные метрики; возможности `max_body_length=3`, контекстных предикатов `uses_build_tool`/`uses_runtime` и устойчивости к шуму на нём не видны.

**Итоговая оценка готовности:** к показу — высокая после 1–2 дней работ уровня P0; к исследовательской части (конференция, статья, защита) — средняя, требуется блок P2 с кросс-валидацией, абляциями и данными, где метод не обязан быть идеальным.

### 3.3. Пункты ТЗ, требующие отдельного внимания

1. **П. 5.2 vs 6.2 (пустой `labels`).** В ТЗ есть противоречие: в 5.2 пустой список — «ошибок нет», в 6.2 — «известные ошибки не размечены». Проект выбрал закрытый мир и зафиксировал это в README — это корректное и хорошо объяснённое решение. Для полноты стоит добавить в схему необязательное поле `label_status: "verified" | "unverified"` или отдельный флаг, чтобы можно было импортировать данные с реально неизвестной разметкой, не превращая их молча в отрицательные примеры.
2. **П. 7.2 (три статуса).** Сейчас есть `detected`, `not_detected`, `no_rules`; статус «недостаточно данных» из-за неизвестных полей не выделен. Это ближайший содержательный пробел по ТЗ.
3. **П. 11 (примеры экспорта).** Формально примеры есть, но они сгенерированы заглушкой и содержат нерепрезентативное время; перед сдачей нужно перегенерировать реальным SWI-Prolog.
4. **П. 14 (источники).** В README нет ссылок на Cropper & Morel, Popper, `library(http/json)`, Janus. Это не обязательное требование, но для исследовательской работы — желательный минимум.
5. **П. 9.2 (несколько seed).** Сделано (1/3/5 запусков), но это не кросс-валидация; для более сильной экспериментальной части стоит добавить repeated stratified k-fold.

## 4. Сильные стороны, которые стоит сохранить

- **Честный ILP-контур.** Метки не попадают в BK; язык гипотез задан словарём `bk_predicate/2`; кандидаты строятся из словаря, а не из списка правил. Это ключевое требование ТЗ и оно выполнено аккуратно.
- **Канонизация и дедупликация.** `canonical_body/2` сводит перестановки литералов и переименования переменных, поэтому поиск не тонет в изоморфах.
- **Отсечение по монотонности.** Тело, не набравшее `min_support`, не уточняется — это корректно, потому что добавление литерала может только уменьшить покрытие.
- **Журнал отказов.** Показаны лучшие отклонённые кандидаты с причинами; на демо это наглядно объясняет, почему `package_absent` сам по себе не правило.
- **Изоляция Prolog.** `subprocess` без shell, временный каталог, ASCII-имена запроса/ответа, обработка всех типов сбоев, `ILP_KEEP_TEMP` для отладки.
- **Генератор с дистракторами.** Отсутствующие, но не требуемые пакеты; несоответствия версий у не требуемых пакетов; лишние build tools/runtimes. Это делает задачу не тривиальной и подтверждает, что правило должно связывать два факта одной переменной.
- **Тесты.** Независимый Python-проверяльщик покрытия, сверка TP/FP/FN, AC-07, JSON-протокол, plunit. Для учебного проекта это выше среднего.
- **Документация.** README подробный, с установкой, типичными ошибками, сценарием демонстрации, архитектурой и ограничениями.

### 6.2. P1 — соответствие ТЗ и убедительность демонстрации (3–7 дней)

**6. Третий статус «недостаточно данных».**
Самый дешёвый и самый заметный шаг к п. 7.2 ТЗ. Реализация не требует менять Prolog:
- после `parse_diagnosis` для каждого класса, где `status == "not_detected"`, проверить, какие поля нужны правилам этого класса;
- если среди них есть `null`-поля проекта → `status = "insufficient_data"`, вернуть `missing_fields`;
- в UI: серый/жёлтый статус «недостаточно данных: неизвестны поля …», а не «не обнаружен»;
- в `predicted_labels` для метрик считать такой класс как «не обнаружен» (или исключать из метрик — зафиксировать политику);
- тест: проект с `required_packages: null` и правилом, которому нужно это поле.

**7. Импорт модели.**
Добавить `load_model_document(text) -> dict` с проверкой:
- `format == "prolog-ilp-diagnostics/model"`, `format_version`;
- наличие `model.rules`, корректность `target`/`body`/`var`;
- сохранение `params`, `dataset`, `environment`;
- кнопку «Загрузить модель (JSON)» на странице обучения/экспорта;
- тест round-trip: обучить → экспортировать → импортировать → диагностировать тот же проект → тот же результат.

Это превращает экспорт из «сувенира» в рабочий сценарий и упрощает показ: можно один раз обучить, сохранить модель и не зависеть от времени обучения на сцене.

**8. «Трудный» генератор и константы в языке гипотез.**
На демо-наборе все правила длины 2, а `uses_build_tool`/`uses_runtime` не используются. Предлагаемая эволюция:
- добавить в язык гипотез литералы-константы: `uses_build_tool(Project, poetry)`, `uses_runtime(Project, python)`;
- в генераторе сделать режим `hard`, где ошибка наступает только при определённом контексте: например, `missing_dependency` — если пакет требуется, отсутствует **и** сборка `poetry`; `incompatible_version` — если runtime `python` и версия не совпала;
- тогда ILP будет вынужден строить правила длины 3, а `max_body_length=2` покажет деградацию, а `=3` — восстановление. Это сильный и наглядный эксперимент, которого сейчас не хватает.

Технически: заменить `Pred-N` на `Pred-N` / `Pred-const(Value)`, научить `canonical_body`, `materialise`, `refine`, `rule_text`, `data_io` и тесты; ограничить константы top-K значениями, чтобы не взорвать поиск.

**9. Наборы данных для разных демонстраций.**
Добавить:
- `data/demo_partial.json` — 10–20 % проектов с `null`-полями; показать «неизвестно ≠ отсутствует»;
- `data/demo_hard.json` — условные ошибки, правила длины 3;
- `data/demo_noisy.json` — шум меток 10–20 % и/или противоречивые примеры; показать падение precision и работу порогов;
- `data/demo_unlabeled.json` — проекты без меток (если реализуете `label_status`), чтобы показать, что они не становятся отрицательными.

Переключатель наборов на странице «Данные» + короткое описание, что именно демонстрирует каждый.

**10. Расширить UI-тесты.**
`AppTest` уже умеет нажимать кнопки. Добавить сценарий:
- загрузить демо → проверить `n_projects == 500`;
- обучить → проверить 4 правила и `model["dataset"]["n_train"] == 400`;
- диагностировать `pandas` → проверить `detected` и `Package = pandas`;
- загрузить проект с `required_packages: null` → проверить `insufficient_data`;
- импортировать модель → проверить, что правила совпали.
Такой тест ловит именно те расхождения, которые сейчас видны только глазами.

**11. Пакетная диагностика и анализ ошибок.**
Сейчас эксперимент показывает агрегированные метрики, но не показывает, **на каких проектах** модель ошиблась. Добавить страницу/блок:
- выбрать test-выборку (из эксперимента или загрузить свой JSON с метками);
- прогнать `engine.diagnose` пакетом (движок это уже умеет);
- таблица: `id`, истинные метки, предсказанные, сработавшие правила, FP/FN;
- матрица ошибок по классам;
- клик по проекту → объяснение и «почему не сработало» (ближайшее правило, какой литерал не выполнился).

Это одновременно улучшает демонстрацию и даёт материал для раздела «анализ ошибок» в отчёте.

**12. Ограничить перебор доказательств.**
В `rule_match` заменить `findall` всех доказательств на `limit(MaxProofs, ...)` (с последующей сортировкой) или `call_nth`. Добавить тест: проект с 100 пакетами, правило из 3 литералов, `max_proofs=3` — диагностика не должна замедляться квадратично.

### 6.3. P2 — исследовательская часть (1–2 недели)

**13. Полноценная экспериментальная программа.**
Сейчас есть один split, 1/3/5 seed и шум 0/5/10 %. Для конференции/защиты этого мало. Добавить:
- repeated stratified k-fold (например, 5×2) с одинаковыми фолдами для ILP и DT;
- доверительные интервалы (bootstrap) для macro-F1/micro-F1/exact-match;
- McNemar или парный тест по проектам для сравнения ILP и DT;
- learning curves: качество vs `n_train` (50, 100, 200, 400, 800);
- абляции: `max_body_length` 1/2/3/4, `min_support` 1/2/5, `min_precision` 0.5/0.8/0.95, шум 0/5/10/20 %, language bias без контекстных предикатов, без упрощения;
- отдельный замер времени инференса (не только обучения).

Результаты — в `results/` + сводная таблица в `docs/experiment.md`. Это самый большой прирост «исследовательской ценности» на единицу усилий.

**14. Метрики восстановления правил, а не только предсказания.**
Генератор знает истинные правила по построению. Добавить:
- точность восстановления: совпало ли выученное правило с порождающим (exact match по литералам);
- literal-level precision/recall;
- стабильность набора правил между seed (Jaccard);
- «выучил ли алгоритм лишнее» — число правил сверх истинного.

Это отвечает на вопрос «модель угадала корреляцию или действительно восстановила правило», который неизбежно зададут на защите.

**15. Данные, приближенные к реальным.**
Синтетика с идеальной разделимостью — главное ограничение. Варианты:
- собрать 30–100 реальных Python-проектов: `requirements.txt`/`pyproject.toml` → required; `pip freeze`/lock → present/absent; `.env.example` → config keys; README/CI → env vars; наличие `poetry.lock`/`Pipfile` → build tools;
- разметить ошибки вручную по истории issue/CI-логам (хотя бы 50 проектов);
- или сделать «полуреальные» данные: реальные словари пакетов/ключей/переменных и реалистичные распределения, но метки по построению. Это дешевле и всё равно полезнее текущих 30 пакетов.

В README добавить раздел «Threats to validity»: синтетика, закрытый мир, идеальная разделимость, один язык (Python-экосистема), отсутствие реальных конфигураций.

**16. Масштабирование и кэширование покрытия.**
Для 1000 проектов сейчас 0.5 с — отлично. Для 5–10 тыс. и `max_body_length=4` понадобится:
- кэш `covers(Body, Id)` или покрытия тела целиком;
- вычисление покрытия ребёнка как фильтрация покрытия родителя по новому литералу (монотонность);
- инвертированные индексы «предикат–значение → проекты»;
- бенчмарк `scripts/benchmark.py` на 500/1000/5000 проектов и график времени.

Это также хороший инженерный раздел отчёта: «как масштабируется ILP-поиск».

**17. Улучшения алгоритма (по желанию, но сильно украшают работу).**
- **Beam search / Foil gain**: вместо полного перебора уровня — ранжирование уточнений по приросту и удержание top-K; меньше кандидатов, лучше обобщение на шумных данных.
- **Внутренняя валидация**: делить train на train/validation для выбора правил, а не только порогов; это честнее, чем greedy по train.
- **Отрицание как failure**: `\+ package_absent(Project, Package)` для «пакет требуется и присутствует»; требует корректной семантики неизвестного.
- **Bottom clause / mode declarations** (Progol/Aleph/Popper-стиль) — более «настоящий» ILP, но это уже отдельный исследовательский этап.
- **Статистическая значимость**: likelihood ratio, Laplace-corrected precision, минимальный lift — чтобы не выбирать случайные правила на малых поддержках.

**18. Объяснения «почему не сработало» и контрфакты.**
Сильная сторона проекта — объяснимость; её можно усилить:
- для несработавшего правила показывать первый невыполненный литерал («требуется `package_absent(new_project, pandas)`, но такого факта нет»);
- для сработавшего — контрфакт: «если бы не было `package_absent`, правило бы не сработало»;
- для правила — список покрытых положительных и ошибочно покрытых отрицательных проектов (ID + краткая причина).

Это почти бесплатно на Python (факты уже есть) и очень выигрышно на демонстрации.

## 10. Приложение B. Предлагаемый контракт для третьего статуса

Ответ Prolog можно не менять; статус вычисляется в Python:

```json
{
  "id": "new_project",
  "classes": {
    "missing_dependency": {
      "status": "insufficient_data",
      "missing_fields": ["required_packages"],
      "matches": []
    },
    "missing_config_key": {
      "status": "not_detected",
      "missing_fields": [],
      "matches": []
    }
  }
}
```

Правило вычисления: `insufficient_data`, если ни одно правило класса не сработало, но хотя бы одно правило класса использует предикат, соответствующее поле которого в проекте `null`/отсутствует. Иначе — `not_detected`.
