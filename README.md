# Прототип ИИ-системы диагностики ошибок конфигурации на основе ILP (Prolog)

Локальное веб-приложение (Streamlit), в котором **SWI-Prolog сам выводит диагностические правила**
из размеченных примеров и фоновых знаний, затем применяет их к новым проектам и объясняет
срабатывание. Заранее написанных правил в проекте нет: есть только словарь допустимых предикатов
(language bias) и общий алгоритм поиска.

* Python 3.11+ — данные, интерфейс, запуск Prolog, сравнение с решающим деревом, экспорт.
* SWI-Prolog 9.x или 10.x — генерация гипотез, проверка покрытия логическим выводом, оценка и отбор правил.
* Без GPU, без облачных API; ориентир — обычный ПК с 16 ГБ ОЗУ.

> **Проверено на Windows:** ниже перечислены версии и команды последнего локального прогона.
> Linux/macOS и чистая машина без Python/SWI-Prolog отдельно не проверялись.

## Запуск в Docker (Windows, macOS, Linux)

Установите и запустите **Docker Desktop** (на Linux — Docker Engine и Compose plugin), затем из папки проекта выполните:

```powershell
docker compose up --build -d
```

Откройте <http://localhost:8501>. В контейнер уже входят приложение, Python-зависимости и SWI-Prolog; устанавливать Python и Prolog на ноутбук отдельно не нужно. Сборка требует подключения к интернету для загрузки базового образа и пакетов. Первый запуск занимает больше времени, последующие используют собранный образ.

Полезные команды:

```powershell
docker compose logs -f app  # журналы приложения
docker compose down         # остановить приложение
docker compose up --build -d  # пересобрать и запустить после обновления файлов
```

Результаты, сохраняемые приложением в `results/`, остаются в Docker-томе `results` после остановки и пересоздания контейнера. `docker compose down -v` удалит этот том вместе с сохранёнными результатами. По умолчанию веб-интерфейс доступен только на этом ноутбуке (`127.0.0.1`); чтобы открыть его в локальной сети, замените в `compose.yaml` привязку порта `"127.0.0.1:8501:8501"` на `"8501:8501"`.

Если порт `8501` занят, поменяйте только левую часть привязки, например на `"127.0.0.1:8502:8501"`, и откройте `http://localhost:8502`. Тайм-аут Prolog можно изменить в `.env`, добавив `ILP_TIMEOUT_SECONDS=600`.

## 1. Установка (Windows 10/11)

```powershell
# 1. Создать виртуальное окружение
python -m venv .venv

# 2. Активировать его (PowerShell)
.venv\Scripts\Activate.ps1
# если PowerShell запрещает скрипты:  Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
# (в cmd.exe:  .venv\Scripts\activate.bat)

# 3. Установить зависимости
pip install -r requirements.txt

# 4. Установить SWI-Prolog отдельно и проверить
swipl --version

# 5. Запустить приложение
streamlit run app.py
```

Либо просто дважды щёлкните **`run.bat`**: он создаст `.venv`, установит зависимости и запустит приложение.
(Linux/macOS: `./run.sh`.)

### Установка SWI-Prolog

1. Скачайте стабильную версию 9.x: <https://www.swi-prolog.org/Download.html> (раздел *Stable release*, Windows 64-bit).
2. В установщике **отметьте «Add swipl to the system PATH for all/current user»**.
3. Откройте **новое** окно PowerShell и выполните `swipl --version` — должна вывестись версия.

**Если swipl не в PATH**, есть два способа указать его вручную:

* в боковой панели приложения — поле «Путь к swipl» (например `C:\Program Files\swipl\bin\swipl.exe`);
* либо скопируйте `.env.example` в `.env` и задайте `SWIPL_PATH=C:\Program Files\swipl\bin\swipl.exe`.

Приложение само ищет `swipl` в PATH и в типовых каталогах `C:\Program Files\swipl\bin`.

### Проверка установки

```powershell
python scripts/make_examples.py           # сквозной сценарий без браузера (обучение, диагностика, эксперимент)
```

Путь к проекту лучше без нестандартных символов, но кириллица в пути пользователя допустима:

## 2. Типичные ошибки запуска

| Сообщение / симптом | Причина и решение |
|---|---|
| «SWI-Prolog не найден…» в интерфейсе | `swipl` нет в PATH. Добавьте папку `bin` в PATH, перезапустите терминал или укажите путь в боковой панели / `.env`. |
| `swipl` не опознан в PowerShell после установки | Открыто старое окно терминала. Закройте и откройте новое. |
| «SWI-Prolog не уложился в N с» | Слишком большой перебор. Уменьшите `max_body_length` до 2, поднимите `min_support`, либо увеличьте `ILP_TIMEOUT_SECONDS` в `.env`. |
| «SWI-Prolog не вернул ответ» + текст stderr | Ошибка загрузки Prolog-файлов или версия слишком старая. Текст из stderr показан в сообщении. Для отладки задайте `ILP_KEEP_TEMP=1` — временные файлы запроса/ответа сохранятся. |
| «Логическое ядро сообщило об ошибке: …» | Ядро поймало исключение (например, неверное правило); сообщение содержит причину. |
| «некорректный JSON (строка N, столбец M)» | Файл повреждён или не в UTF-8. Пример проверки — `data/invalid_example.json`. |
| `ModuleNotFoundError` | Не активировано `.venv` или не выполнен `pip install -r requirements.txt`. |
| Предупреждение «достигнут max_candidates» | Поиск остановлен предохранителем. Увеличьте лимит или ужесточите язык (`max_body_length`). |

## 3. Как пользоваться (и сценарий демонстрации на конференции)

1. **Данные → «Демонстрационный набор» → «Загрузить»**. Покажите число проектов (500), распределение четырёх
   классов, долю проектов с несколькими ошибками и таблицу проектов.
   Для проверки валидации загрузите `data/invalid_example.json` — приложение укажет запись и поле каждой ошибки.
2. **Обучение ILP** → параметры по умолчанию (`max_body_length=3`, `min_support=2`, `min_precision=0.80`,
   `max_rules_per_class=5`) → «Запустить обучение». Покажите выученные правила: у каждого — подсветка,
   support/TP, FP, FN, precision, recall, F1. Разверните журнал: сколько кандидатов сгенерировано и проверено,
   какие кандидаты отклонены и почему (например, одиночный `package_absent(Project, Package)` отклонён по точности:
   «пакет отсутствует» ≠ «пакет требуется и отсутствует»).
3. **Диагностика → «Ввести вручную»**. В форме уже стоит пример: пакет `pandas` требуется и отсутствует,
   `scipy` отсутствует, но не требуется. Нажмите «Запустить диагностику»: статус «обнаружен» только у
   `missing_dependency`; видны текст правила, подстановка `Package = pandas` и факты
   `requires_package(new_project, pandas)`, `package_absent(new_project, pandas)`.
   Замените `pandas` на никогда не встречавшееся имя пакета — правило обобщится, ведь оно оперирует переменной.
   Те же факты (с другим id) есть в `data/example_project_missing_dependency.json` (режим «Загрузить JSON одного проекта»).
4. **Эксперимент**: seed 42, test 20 %, шум 0 % → «Запустить сравнение». Покажите таблицу и графики
   ILP и Decision Tree на одной и той же тестовой выборке, время обучения и сложность моделей.
   Затем сравните repeated stratified k-fold, кривую обучения и абляции `max_body_length`,
   `min_support` и `min_precision`. Для устойчивости к шуму доступны уровни 0–20 %.
5. **Экспорт / О проекте**: модель (JSON), правила (`.pl`), набор данных, версии ПО, ограничения.

### Пример JSON для импорта (`schema_version 1.0`)

```json
{
  "schema_version": "1.0",
  "projects": [
    {
      "id": "project_001",
      "labels": ["missing_dependency"],
      "facts": {
        "required_packages": ["numpy", "pandas"],
        "absent_packages": ["pandas"],
        "version_mismatches": [],
        "required_config_keys": ["DATABASE_URL"],
        "absent_config_keys": [],
        "required_env_variables": ["API_TOKEN"],
        "absent_env_variables": [],
        "build_tools": ["pip"],
        "runtimes": ["python"]
      }
    }
  ]
}
```

Для диагностики одного проекта достаточно объекта `{id, facts[, labels]}`.

## 4. Принцип обучения (ILP)

**Цель:** `has_error(Project, ErrorType)`, `ErrorType ∈ {missing_dependency, incompatible_version, missing_config_key, missing_environment_variable}`;
задача многометочная, для каждого класса — своя пара E+ / E−.

**Фоновые знания (BK)** — факты о проектах, всегда привязанные к id проекта:
`requires_package/2`, `package_absent/2`, `version_mismatch/2`, `requires_config_key/2`, `config_key_absent/2`,
`requires_env_variable/2`, `env_variable_absent/2`, `uses_build_tool/2`, `uses_runtime/2`.
Метки `labels` **никогда** не попадают в BK: они используются только для формирования E+ и E−.

**Language bias (задаётся человеком):** голова — `has_error(Project, Class)`; тело — до `max_body_length`
литералов из словаря выше. Поддерживаются положительные литералы, отрицания `\+`, неравенство `\=`
между связанными переменными одного типа и константы для `uses_build_tool/2` и `uses_runtime/2`.
`Project` общий для всех литералов; переменные типизированы (пакет / ключ / переменная окружения /
сборка / среда) и могут повторяться, чтобы выразить связь «один и тот же объект».

**Алгоритм (файл `prolog/ilp_engine.pl`, сверху вниз по уровням):**

1. *Подготовка:* загрузка BK, формирование E+/E− для каждого класса.
2. *Генерация:* уровень 1 — все однолитеральные тела; каждое тело уточняется добавлением одного литерала
   (с уже имеющейся или новой переменной того же типа). Изоморфные тела (перестановка литералов,
   переименование переменных) сводятся к каноническому виду и **удаляются как дубликаты**.
3. *Проверка покрытия:* логический вывод Prolog (`covers/2`) доказывает тело на фактах каждого обучающего
   проекта. Покрытие вычисляется один раз на тело, затем считается для каждого класса: TP, FP, FN.
4. *Оценка:* support = TP; метрики отображают обычную precision/recall/F1. Отбор использует сглаженную
точность (m-оценку) и MDL-подобный штраф за сложность; `min_precision` применяется к сглаженной точности.
5. *Отсечение:* добавление литерала может лишь уменьшить покрытие, поэтому тело, у которого TP < `min_support`
   для всех классов, не уточняется. Предохранитель `max_candidates` останавливает поиск с предупреждением.
6. *Отбор:* порогами `min_support` и `min_precision`; первое правило класса — лучшее по F1
   (при равенстве — короче, затем больше TP); далее жадно добираются правила, покрывающие ещё не покрытые
   положительные примеры, до `max_rules_per_class`.
7. *Упрощение:* литералы, не меняющие покрытие обучающей выборки, удаляются; правила, чьи положительные
   примеры целиком покрыты остальными, отбрасываются. Тестовая выборка в этом не участвует.
8. *Вывод:* правила, метрики на train, журнал по уровням, лучшие отклонённые кандидаты с причинами
   (`low_support`, `low_precision`, `no_new_positives`, `rule_limit_reached`), статистика, время.

Если для класса надёжного правила нет, интерфейс показывает «Недостаточно данных для построения надёжного правила».

**Диагностика** (`diagnose_projects/4`): Prolog загружает факты нового проекта, доказывает тела выученных правил
и возвращает не только факт срабатывания, но и подстановки переменных и конкретные подтверждающие факты.
«Неизвестно» (`null`) не равно «отсутствует»: интерфейс предупреждает, если правилу нужны неизвестные поля.

### Параметры

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `max_body_length` | 3 (1–3) | максимум условий в теле правила |
| `min_support` | 2 | минимум покрытых положительных обучающих примеров (TP) |
| `min_precision` | 0.80 | минимальная точность правила на обучающей выборке |
| `max_rules_per_class` | 5 | максимум правил на класс |
| `max_candidates` | 20000 | предохранитель: максимум проверяемых тел правил |

## 5. Данные

* **Политика неизвестных полей:** игнорируются **с предупреждением** (на уровне проекта и в `facts`).
* **Некорректная запись** исключается из набора и попадает в отчёт (запись + поле); если корректных записей
  нет — набор отклоняется. Дубликаты `id` — ошибка (повторная запись отбрасывается), дубликаты значений
  в списках нормализуются с предупреждением. Элемент списка — строка либо объект `{"name": "..."}`.
* **`labels: []`** — проект проверен, известных ошибок нет: отрицательный пример для всех классов
  (так сказано в разделе 5.2 ТЗ). Отсутствие/`null` в `labels` — ошибка записи: неизвестная разметка
  не должна молча превращаться в «нет ошибок».
* **«Неизвестно» ≠ «отсутствует»:** `facts.<поле>: null` или отсутствие поля — «неизвестно»;
  `[]` — «известно, что пусто». Для Prolog оба случая дают отсутствие фактов, но различаются в интерфейсе.
* **Генератор** (`core/generator.py`): воспроизводим по `(n, seed, error_rate)`. Метки строятся «по построению»
  (сначала выбирается внедряемая ошибка, затем факты), а не вычисляются правилом. Есть дистракторы:
  отсутствующие, но не требуемые пакеты/ключи/переменные; несоответствия версий у не требуемых пакетов;
  лишние системы сборки и среды выполнения. Поэтому `package_absent` сам по себе — неверный признак.
  Независимая проверка согласованности меток и фактов — в `tests/`.

## 6. Эксперимент

Один `seed` → одно разбиение train/test (80/20, стратификация по сочетанию меток); ILP и дерево
обучаются на одном train и предсказывают один test. Кодировщик признаков и дерево видят только train.
Шум меток (0/5/10 %) добавляется **только в train**, воспроизводимо по seed: каждая пара «проект–класс»
независимо меняет значение с заданной вероятностью. Метрики: precision/recall/F1 по классам, macro/micro-F1,
exact-match; время обучения; сложность (правил, среднее число условий, число литералов, доля покрытых train).
Параметры, seed, размеры выборок и версии библиотек сохраняются в JSON результатов (кнопка «Сохранить в results/»).

Сравниваются три модели:

1. **ILP (Prolog)**;
2. **Decision Tree** (основной базовый метод, `MultiOutputClassifier(DecisionTreeClassifier)`) — на «плоских»
   бинарных признаках «значение X требуется / отсутствует …», словарь строится по train;
3. **Decision Tree + агрегаты** — тот же метод плюс четыре числа «сколько элементов одновременно требуется и
   отсутствует» (из фактов, без меток). Это вручную внесённое реляционное знание, поэтому вариант показан отдельно
   и не подменяет основной базовый метод.

**Как читать результаты.** На синтетических данных ILP находит правила с precision = recall = 1.0, потому что метки
по построению точно выражаются языком гипотез; это верхняя граница, а не оценка на реальных проектах.
Плоское дерево заметно слабее, так как должно «выучить» связь «тот же пакет» по отдельным признакам каждого пакета
и не обобщается на не виденные имена; на чистых данных дерево с агрегатами решает задачу так же хорошо, как ILP (при шуме меток результаты расходятся — смотрите страницу «Эксперимент»).
Время ILP включает запуск процесса SWI-Prolog. Выводы следует делать по фактическим измерениям на вашей машине.

## 7. Архитектура

```
app.py                  точка входа Streamlit
ui/pages.py             страницы (только интерфейс), ui/components.py — правила, таблицы, графики
core/dataset.py         схема, валидация, нормализация, сводка
core/generator.py       воспроизводимый генератор синтетических проектов
core/prolog_runner.py   поиск swipl, запуск подпроцесса, JSON-обмен, обработка ошибок и тайм-аутов
core/diagnosis.py       разбор ответа диагностики, объяснения, предупреждения о «неизвестно»
core/feature_encoder.py плоские признаки для дерева (словарь только по train)
core/evaluation.py      разбиение, шум, метрики, дерево, эксперимент, несколько seed
core/exports.py         модель JSON/.pl, диагностика JSON/CSV, эксперимент
core/settings.py        .env, пути
prolog/ilp_engine.pl    ILP-алгоритм, покрытие, диагностика, точка входа
prolog/data_io.pl       схема BK и классов, чтение/запись JSON
prolog/tests.pl         plunit-тесты
scripts/                generate_demo_dataset.py, make_examples.py
data/  examples/  results/
```

**Обмен Python ↔ Prolog.** Python пишет `request.json` во временную папку и запускает без shell:

```
swipl -q -g main -t halt prolog/ilp_engine.pl -- request.json response.json
```

(аргументы — отдельными элементами списка, рабочий каталог — временная папка). Prolog читает запрос, выполняет
команду (`train` / `diagnose` / `ping`) и пишет JSON-ответ в файл; консольный вывод в ответ не попадает.
Обработаны: отсутствие swipl, сбой запуска, тайм-аут, пустой ответ, некорректный JSON, статус `error`.
Ядро выбирает библиотеку `library(json)` (SWI-Prolog ≥ 9.3) или `library(http/json)` (более ранние 9.x).

## 8. Тесты

```powershell
pytest                                        # Python + интеграция с swipl (без swipl интеграционные тесты пропускаются)
swipl -g run_tests -t halt prolog/tests.pl    # plunit
```

Что проверяется: валидация и сообщения об ошибках; воспроизводимость и корректность генератора (независимо);
метрики, разбиение, шум, кодировщик; **изменение обучающих примеров меняет модель** (AC-07: снятие меток класса убирает
правило; перенос меток на другой класс «переносит» правило); отсутствие правила на несвязанных метках; совпадение
TP/FP/FN из Prolog с независимым подсчётом на Python; совпадение диагностики с независимым Python-проверяльщиком;
подстановки и факты-основания; обобщение на не виденный пакет; предупреждение `max_candidates`; одинаковая
тестовая выборка у обоих методов; эвристика отсутствия готовых правил в исходниках; сквозной JSON-протокол.

## 9. Ограничения текущей версии

* Язык гипотез ограничен заданным словарём, типами переменных и текущим `max_body_length` (1–3 в UI);
  константы доступны только для build tools и runtimes. Это ограничивает то, какие отношения система способна выучить.
* Метки считаются полными (закрытый мир): проект без меток — отрицательный пример.
* Демо-синтетика не заменяет оценку на независимых реальных проектах. Режим `hard` содержит контекстные
  условия, `partial` — неизвестные поля. Метрики восстановления правил применимы только к наборам с
  опубликованной генератором разметкой истинных правил.
* Система обнаруживает только закономерности, выученные из данных; отсутствие срабатывания не гарантирует
  корректность проекта. Подсказки ремонта текстовые: файлы автоматически не изменяются.
* Парсер реальных проектов ограничен поддерживаемыми форматами манифестов и lock-файлов; если источник
  отсутствует, поле остаётся неизвестным. Проверяйте распознанные факты перед интерпретацией результата.

## 10. Решения по неоднозначностям ТЗ

* **Пустой `labels`:** в разделе 5.2 это «нет ошибок» (E−), в 6.2 — «известные ошибки не размечены». Принято
  согласованное толкование «известных ошибок нет» (закрытый мир); неизвестная разметка = отсутствие поля.
* **Отдельный базовый вариант с агрегатами** добавлен сверх ТЗ, чтобы честно показать вклад реляционной информации.
* **Единая команда `diagnose`** для одного проекта и для пакетной оценки тестовой выборки (`max_proofs=0` — только вердикт),
  чтобы эксперимент не запускал процесс Prolog на каждый проект.
* **Источники:** ILP следует общей generate–test–constrain постановке; примеры классических индуктивных систем —
  Cropper & Morel, *An Introduction to Inductive Logic Programming* ([arXiv:2000.02259](https://arxiv.org/abs/2000.02259))
  и Popper ([документация проекта](https://github.com/logic-and-learning-lab/Popper)). Этот проект реализует
  собственный ограниченный level-wise поиск, а не Popper. Интеграция использует
  [SWI-Prolog command line](https://www.swi-prolog.org/pldoc/man?section=cmdline) и
  [JSON library](https://www.swi-prolog.org/pldoc/man?section=json); [Janus](https://www.swi-prolog.org/pldoc/man?section=janus)
  рассмотрен как возможный способ интеграции, но сейчас не используется.
